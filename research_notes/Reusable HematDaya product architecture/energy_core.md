# Reusable HematDaya energy core and extension boundaries

## What is the smallest defensible reusable architecture?

### Takeaway
Build a proposed modular monolith whose public use cases accept normalized readings and return scope-safe energy summaries and evidence-bearing findings. Keep household and industrial calculations in ordinary optional modules, and put protocols, storage, and delivery mechanisms behind narrow adapters; these are recommendations, not evidence that a reusable HematDaya implementation already exists.

### Cited Findings
- **Original architecture source:** Cockburn's 2005 ports-and-adapters article says applications should be driven by people, programs, tests, or batch scripts and developed independently of runtime devices/databases. Technology-specific adapters translate external events into application calls/messages; the application does not need to know the input technology. This directly supports one ingestion/use-case boundary shared by mobile input, CSV, and future telemetry. — [Cockburn, original Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture)
- **Original practitioner guidance:** Brown's package-by-component proposal groups related business logic and persistence behind a defined component interface. He emphasizes restricting access to implementation details, and warns that folder diagrams alone do not prevent consumers bypassing business rules. This is modularity within one application, not a requirement for separate services. — [Brown, Modular monolith and package by component](https://simonbrown.je/modular-monolith/)
- **Product documentation:** Emoncms separates incoming inputs from stored feeds: processing can calibrate, combine, or convert an incoming value before recording it. Its processing steps run sequentially for each input update. — [OpenEnergyMonitor, Inputs](https://docs.openenergymonitor.org/emoncms/inputs.html)
- **Product documentation:** ThingsBoard accepts telemetry through multiple protocols and maps differing payload formats into one internal format. Its documented processing path resolves identity/authentication before transformation and persistence. This is evidence of the pattern, not a recommendation to deploy ThingsBoard. — [ThingsBoard, Time-Series Data](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/); [ThingsBoard, Architecture Overview](https://thingsboard.io/docs/reference/architecture/)

### Inferences
- **Proposed shared domain core:** site and access scope; asset/metering-scope relationships; source/channel identity; measurement validation and normalization; interval energy derivation; comparable period summaries; quality/coverage; non-overlapping aggregation; finding records with evidence. These responsibilities remain the same whether the subject is a refrigerator, irrigation pump, compressor, or production line. This division applies Cockburn's technology-independent application boundary and Brown's component encapsulation. — [Cockburn](https://alistair.cockburn.us/hexagonal-architecture); [Brown](https://simonbrown.je/modular-monolith/)
- **Proposed optional calculation modules:** tariff/cost estimation; operating schedules and outside-hours rules; production/output intensity; equipment-specific rules; weather or occupancy adjustments. A module consumes the core's canonical quantities and context and returns a derived metric or finding. It should not import device protocols, reach into another module's tables, or redefine energy semantics. Simple function/service interfaces suffice; no dynamic plugin loader, generic workflow builder, or separate deployment per rule is justified by this task. — Design inference from [Brown](https://simonbrown.je/modular-monolith/) and [Emoncms processing separation](https://docs.openenergymonitor.org/emoncms/inputs.html).
- **Proposed adapters:** manual/CSV ingestion first; specific meter/API/MQTT/Modbus mapping only when a real data source requires it; PostgreSQL persistence; API/mobile/report delivery; worker invocation of the same use cases. The proposed Expo/FastAPI/PostgreSQL/worker stack can implement this boundary, but the research does not establish it as the only or best stack. — Design inference from [Cockburn](https://alistair.cockburn.us/hexagonal-architecture) and [ThingsBoard's transport normalization](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/).
- **A concrete small boundary:** ingestion calls `ingest_readings`; calculation calls `summarize_energy(scope, period)`; an applicable rule calls that summary plus optional context and returns a finding. Keep those interfaces explicit. UI labels, dashboard layout, and onboarding defaults belong to presentation; unit conversion, counter arithmetic, aggregation, rule applicability, and confidence belong to the domain. — Design inference from [Cockburn](https://alistair.cockburn.us/hexagonal-architecture).

### Gaps
- No architecture was implemented or benchmarked during this research. Suggested module names and API shapes are design proposals, not extracted existing code.
- Expected fleet size, samples per second, offline behavior, retention, and actual vendors are unknown. They cannot justify a distributed queue, microservices, Cassandra, or a vendor platform today. ThingsBoard's own architecture distinguishes a single-node PostgreSQL deployment from additional components needed as it scales; its throughput guidance is product-specific rather than a HematDaya capacity claim. — [ThingsBoard, Architecture Overview](https://thingsboard.io/docs/reference/architecture/)

## What must a vendor-neutral electricity measurement contract preserve?

### Takeaway
A timestamp and numeric value are insufficient for correct energy accounting. Preserve quantity, unit, temporal semantics, physical scope, provenance, and quality so the same core can interpret instantaneous power, cumulative meter registers, and interval energy without guessing from field names.

### Cited Findings
- **Product documentation:** Home Assistant gives sensor values a native unit, a device class describing what is measured, and a state class describing the kind of value. Its sensor documentation distinguishes instantaneous measurement, a total that can rise/fall, and a monotonic total that can periodically reset. Reset handling is explicit for one total type and heuristic for another; these choices affect accumulated energy. — [Home Assistant, Sensor entity](https://contributors.home-assistant.io/core/entities/sensor/)
- **Product documentation:** Home Assistant time-weights measurement averages. Its statistics distinguish averages/minimum/maximum from changes in totals; compatible unit changes are converted, incompatible units stop statistics. It also accepts long-term energy statistics supplied directly by integrations, without a live sensor. — [Home Assistant, Long-term statistics](https://www.home-assistant.io/docs/configuration/long-term-statistics/)
- **Product documentation:** Emoncms offers power-to-cumulative-kWh conversion and accumulators that remove counter resets. Its fixed feeds store missing readings as null and display gaps; selecting a feed interval shorter than device reporting does not add detail. — [OpenEnergyMonitor, Inputs](https://docs.openenergymonitor.org/emoncms/inputs.html); [OpenEnergyMonitor, Feeds](https://docs.openenergymonitor.org/emoncms/feeds.html)
- **Product documentation:** ThingsBoard's telemetry contract supports a key, typed value, and timestamp. When a device timestamp is absent, the server supplies it; batches can contain readings with different timestamps. This documents useful transport flexibility but does not itself establish energy-specific units or counter semantics. — [ThingsBoard, Time-Series Data](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/)

### Inferences
- **Proposed channel metadata:** stable `source_id` and `channel_id`; metered `scope_id` separate from the hardware device; `quantity` (initially active power or active energy); declared unit and canonical unit; `value_kind` (`instantaneous`, `cumulative_counter`, `interval_delta`); and flow meaning (`import`, `export`, or signed net). Keep the registry small and explicit. A vendor payload such as `power1` must map to these semantics in its adapter. — Design inference from [Home Assistant sensor semantics](https://contributors.home-assistant.io/core/entities/sensor/) and [ThingsBoard transport normalization](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/).
- **Proposed reading envelope:** source event/import row identity; event time in UTC and receipt time; value; an explicit interval start/end for interval deltas; original unit/value or a link to the raw import; quality (`measured`, `reported`, `derived`, `estimated`, `invalid`); reset marker where available; and derivation/parser version. Retain a site's IANA timezone for calendar buckets, schedules, and tariffs. The exact fields are HematDaya proposals; the sources motivate the distinctions rather than prescribing this schema. — Design inference from [Home Assistant statistics](https://www.home-assistant.io/docs/configuration/long-term-statistics/) and [ThingsBoard timestamped/batched data](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/).
- **Proposed invariants:** dimension-compatible conversions only; no summing samples of watts as kWh; integrate power over elapsed time with a declared gap policy; counter delta only within a valid meter cycle; deduplicate before accounting; reject or quarantine invalid readings; report missing coverage instead of silently turning missing data into zero. Prefer explicit reset metadata and flag ambiguous drops rather than importing another product's reset heuristic unchanged. — Design inference from [Home Assistant sensors](https://contributors.home-assistant.io/core/entities/sensor/), [Home Assistant statistics](https://www.home-assistant.io/docs/configuration/long-term-statistics/), and [OpenEnergyMonitor feeds](https://docs.openenergymonitor.org/emoncms/feeds.html).
- **Proposed summary output:** period boundaries/timezone, quantity/unit, energy value, observed coverage, included source/scope IDs, whether measured or derived, and exclusion/quality reasons. A later tariff or equipment module should consume this output rather than repeat conversion and counter arithmetic. — Design inference from [Emoncms inputs versus feeds](https://docs.openenergymonitor.org/emoncms/inputs.html).

### Gaps
- The compared systems do not provide a single universal electricity schema suitable for adoption unchanged. The proposed contract is a synthesis, not an industry-standard claim.
- No calibration certificates, sample data, import templates, or actual meter reset behavior were supplied. Accuracy, sampling sufficiency, gap interpolation, and device-specific reset rules require validation against real sources.
- Receipt-time timestamps are convenient for live telemetry but cannot reconstruct original event time for delayed uploads. HematDaya must make that quality limitation explicit rather than silently treating receipt time as historical truth; this is a design inference from the server-assigned timestamp option in [ThingsBoard](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/).

## Which energy-specific lessons should govern aggregation, calculations, and advice?

### Takeaway
Reuse the accounting and evidence workflow across both markets; make additional context and rule applicability optional. The most consequential reusable safeguard is physical-scope accounting: a main meter and its submeters describe overlapping consumption and cannot be added indiscriminately.

### Cited Findings
- **Product documentation:** Home Assistant explicitly supports upstream/child device relationships for energy and water. Its example is a breaker measuring a whole circuit alongside individually metered devices on that circuit; configuring the hierarchy prevents duplicate counting. — [Home Assistant, Integrating individual device energy usage](https://www.home-assistant.io/docs/energy/individual-devices/)
- **Product documentation:** Home Assistant's energy configuration allows a single source to start, then additional consumption, production, or storage sources. Available dashboard cards depend on configured energy sources. That is an example of capability-sensitive presentation, not proof that domain rules should reside in dashboard configuration. — [Home Assistant, Home energy management](https://www.home-assistant.io/docs/energy/)
- **Product documentation:** Emoncms processes include calibration, conversion, arithmetic combinations, conditional processing, and schedule-based zero/null handling. Feeds remain separate from incoming inputs. This shows reusable processing primitives but does not validate a particular savings rule or industrial benchmark. — [OpenEnergyMonitor, Inputs](https://docs.openenergymonitor.org/emoncms/inputs.html)

### Inferences
- **Aggregation belongs in the shared core:** record metering containment/overlap explicitly. For a requested scope, select a non-overlapping accounting set: use a main meter for its total and children for attribution, or sum proven disjoint children when coverage is adequate. Never compute `main + children`. Mark `main - known_children` as residual/unallocated energy; missing sources and measurement disagreement can affect it. Do not silently clamp or portray it as a measured appliance. The broader policy is a HematDaya proposal motivated by the concrete double-counting issue in [Home Assistant's hierarchy documentation](https://www.home-assistant.io/docs/energy/individual-devices/).
- **Household optional context:** appliance category, normal usage schedule, budget, known occupancy if supplied. **Industrial optional context:** plant/line/asset grouping, shifts, production output and unit, maintenance context, contract tariff. Neither market should need to populate the other's fields to import readings and see valid energy totals. This is a proposed domain-module split consistent with [component encapsulation](https://simonbrown.je/modular-monolith/).
- **Calculations have prerequisites:** outside-hours consumption requires a declared schedule; kWh per unit requires an output quantity aligned to the same period and scope; cost requires a tariff, currency, and applicable dates. Without these inputs, present energy/coverage and explain which calculation is unavailable. A flat-rate estimate can be the first tariff implementation; demand charges, taxes, or complex contracts should wait for a real requirement. These are proposed guards, not calculations certified by the source systems. — Design inference from [OpenEnergyMonitor's processing and schedule distinctions](https://docs.openenergymonitor.org/emoncms/inputs.html).
- **The smallest advice workflow:** ingest → validate/normalize → derive interval energy → create scope-safe summary → evaluate applicable rule → persist finding → display/export. Rules are normal reviewed code, with applicability, minimum evidence/coverage, evaluation, and an explanation. A finding should retain rule/version, scope, period, observed metric, comparison/baseline, threshold, supporting reading/summary IDs, missing context, assumptions, and suggested next action. A household standby rule and an industrial outside-shift rule can share the same summary/evidence model while using different context. This is a proposed application of [Cockburn's use-case boundary](https://alistair.cockburn.us/hexagonal-architecture), not a feature claim about the compared products.
- **Presentation stays outside the calculation boundary:** household and industrial screens may choose labels, defaults, and visible analyses, but they call the same accounting use cases. A UI toggle must not be the only thing preventing an invalid sum, unsupported rule, or cross-site access. Domain eligibility/validation must apply to imports, workers, and API calls as well. — Design inference from [Cockburn's warning about business logic in UIs](https://alistair.cockburn.us/hexagonal-architecture) and [Brown's warning about bypassed component rules](https://simonbrown.je/modular-monolith/).
- **Adopt versus avoid:** adopt semantic reading types, source provenance, scope-aware sums, explicit processing stages, and capability-sensitive analyses. Avoid a universal IoT platform, arbitrary user scripts, a plugin marketplace, and automatic equipment controls as initial architecture scope. These product documents provide pattern examples, not a vendor selection or proof that their broader automation/control features are needed here. — Design synthesis from [Home Assistant energy](https://www.home-assistant.io/docs/energy/), [OpenEnergyMonitor inputs](https://docs.openenergymonitor.org/emoncms/inputs.html), and [ThingsBoard telemetry](https://thingsboard.io/docs/user-guide/digital-twins/time-series-data/).

### Gaps
- These sources establish architecture and accounting lessons, not the causal effectiveness or expected percentage savings of HematDaya recommendations. A large energy share alone cannot prove waste, identify an appliance, or quantify recoverable savings.
- Rule thresholds, baseline validity, safety constraints, and savings validation need separate energy-domain evidence and pilot data. Equipment-specific advice must not be inferred merely from a generic asset category.
- This research deliberately did not evaluate purchasing/deploying the reference platforms, actual hardware integrations, automated controls, or production performance. Existing HematDaya architecture remains a proposal.
