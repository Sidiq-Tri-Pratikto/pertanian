# Portable TemuRiset design system before application design

Research accessed **31 October 2026, Asia/Jakarta**. Scope: a small reusable system for the responsive web TemuRiset product, with Indonesian UI and English handoff documentation. All TemuRiset token names, component contracts, palettes and validation gates below are **proposed design decisions**, not implemented artifacts or usability findings. The existing product contract remains authoritative for monetary meaning, permissions, versions, evidence and state transitions.

## How should tokens and themes remain portable without overstating standards support?

### Takeaway

Use a single typed token authority, stable semantic aliases and narrowly scoped component tokens. Treat brand themes as alternate visual values for the same roles; distinguish a validated exchange format from the product's own token architecture.

### Cited Findings

- The DTCG technical-reports index lists **2025.10** as Stable, published **28 October 2025**. The published Format Module is a Final Community Group Report, explicitly outside the W3C Standards Track. Pin that published version when interoperability is required; do not substitute a newer preview draft merely because its date is later. — [DTCG technical reports](https://www.designtokens.org/technical-reports/); [Format Module 2025.10](https://www.designtokens.org/tr/2025.10/format/).
- The Format Module defines typed tokens, groups and references. It requires errors for unresolved targets, reference cycles and incompatible referenced types, and includes deprecation metadata. A group is organizational structure rather than evidence of a token's semantic purpose. These are exchange-format requirements, not a prescription that every team adopt a particular three-layer architecture. — [DTCG Format Module](https://www.designtokens.org/tr/2025.10/format/).
- USWDS uses constrained palettes of colors, spacing, typography and other style decisions to reduce unnecessary choice and make designer–developer communication more consistent. Its token system is an implementation example, not a requirement to install USWDS in TemuRiset. — [USWDS design tokens](https://designsystem.digital.gov/design-tokens/).
- Carbon describes a token as a role-based identifier whose role remains stable across themes while values vary. Themes customize existing components through those shared variables. This supports separating identity from component behavior; Carbon's own palette and framework are not mandatory. — [Carbon themes overview](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview).
- USWDS spacing uses an eight-pixel foundation with smaller increments such as four pixels. Its typography guidance recommends a comfortable effective 16-pixel size for most text, left-aligned reading, and a 45–90-character line range with a 66-character target for long text. These are system recommendations, not WCAG minimum-font-size rules. — [USWDS spacing](https://designsystem.digital.gov/design-tokens/spacing-units/); [USWDS typography](https://designsystem.digital.gov/components/typography/).

### Inferences

- Proposed TemuRiset layers are `TR.ref.*` for primitives, `TR.sys.*` for roles and `TR.comp.*` only for component-specific decisions. Examples are `TR.ref.color.teal.700`, `TR.sys.color.action.primary.background` and `TR.comp.button.primary.background`. Components consume semantic/component aliases, never independent copies of the same raw color. This is our application of constrained tokens and stable roles, rather than a DTCG-mandated naming scheme. — Design synthesis from [USWDS](https://designsystem.digital.gov/design-tokens/) and [Carbon](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview).
- Start with one light theme. Suggested seed values are canvas `#F8FAFC`, surface `#FFFFFF`, text `#0F172A`, secondary text `#475569`, primary action `#0F766E`, primary hover `#115E59`, focus `#005FCC`, error `#B91C1C`, success `#166534` and warning text `#92400E`. Pale state backgrounds and neutral borders must be explicitly paired with foreground roles. These are unmeasured seeds: calculate every actual foreground/background pair, then inspect rendered text, icons, borders, disabled states and focus. Do not call this palette accessible based on its names or one screenshot. — Proposed application of [Carbon role stability](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview) and [USWDS in-context verification](https://designsystem.digital.gov/maturity-model/).
- Use a system sans-serif stack initially, 16-pixel-equivalent body text with approximately 1.5 line height, restrained heading steps and 60–70-character reading measures. Auxiliary text can be smaller only where it remains readable and appropriately contrasted. Suggested spacing is 4, 8, 12, 16, 24, 32, 48 and 64; these choices should be rem-based where appropriate. Desktop content can start near 1,200 pixels with 24-pixel gutters, mobile near 16-pixel gutters, then change through content-driven breakpoints. These dimensions are product hypotheses, not external standards. — Proposed starting point informed by [USWDS typography](https://designsystem.digital.gov/components/typography/) and [spacing](https://designsystem.digital.gov/design-tokens/spacing-units/).
- White-label variation can change approved brand, type and surface values, while preserving semantic token identifiers, focus visibility and state meaning. A green brand must not turn success, error and unknown into indistinguishable variants. Business distinctions such as project support versus company equity remain content/model rules rather than theme variables. — Proposed boundary from [Carbon themes](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview).
- Export either validated DTCG 2025.10 tokens with declared supported modules/types, or explicitly labelled custom JSON with its own schema/version and conversion map. Valid JSON alone is insufficient evidence of DTCG conformance. The dotted examples above denote hierarchical logical paths: DTCG JSON must use nested group keys, because literal token/group names cannot contain periods or braces or begin with `$`. Keep aliases and exact units, report unresolved references and retain deprecation mappings rather than silently deleting public token IDs. — Proposed acceptance based on [DTCG Format Module](https://www.designtokens.org/tr/2025.10/format/).

### Gaps

- No tool-specific DTCG importer, resolver, compiler or Claude token binding was exercised. The design-system handoff must record the actual schema, export format and validation result available in its execution environment.
- The palette, typography and layout seeds have not been rendered or tested with users. No claim of WCAG conformance follows from these notes.

## Which components preserve the product's distinctions while keeping the interface simple?

### Takeaway

Build ordinary reusable controls first, then a small set of components that express TemuRiset's evidence, financial scope, shared work and consent. Domain state must be passed explicitly rather than encoded only in color or inferred by a visual component.

### Cited Findings

- GOV.UK components are reusable interface parts that can appear in different patterns and contexts; each has usage guidance and coded examples. Reuse is an aid to consistent services, not a guarantee that combining components produces a usable application. — [GOV.UK components](https://design-system.service.gov.uk/components/).
- GOV.UK contribution criteria distinguish usefulness and uniqueness from readiness to publish. The latter requires usability evidence including disabled users, consistency with existing foundations, versatility and testing across relevant environments. Creating another component merely because a screen differs is therefore a weak basis for expansion. — [GOV.UK contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/).
- GOV.UK advises simplifying a service before adding a task list. Task lists suit work people need to complete across sessions and in flexible order; they are not intended for fixed-order steps or for showing submitted answers. A summary-list pattern serves the latter purpose. — [GOV.UK task list](https://design-system.service.gov.uk/components/task-list/).

### Inferences

- The primitive set should include `TR.Button`, `TR.Link`, `TR.TextField`, `TR.TextArea`, `TR.Select`, `TR.ChoiceGroup`, `TR.Checkbox`, `TR.FieldError`, `TR.ErrorSummary`, `TR.Dialog`, `TR.Disclosure`, `TR.Tabs`, `TR.Status`, `TR.EmptyState` and `TR.SaveState`. Document anatomy, semantic element, accessible name, keyboard/focus behavior, layout limits, states and token aliases for each. One normal form field should not become a different component for every persona. — Proposed reuse application of [GOV.UK components](https://design-system.service.gov.uk/components/) and [contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/).
- A compact domain inventory is `TR.ContextSwitcher`, `TR.InventionCard`, `TR.FundingRequestCard`, `TR.FinancialScope`, `TR.RequirementRow`, `TR.FactSource`, `TR.DocumentItem`, `TR.RevisionItem`, `TR.ScheduleSlotList`, `TR.PartnershipConsent` and `TR.VersionConflict`. Retain only components actually used by the required journeys. A compositional card should show problem, current stage, requested support, three short reasons and a next action, with technical scoring secondary. — Proposed context-specific components, applying [GOV.UK's usefulness criterion](https://design-system.service.gov.uk/community/contribution-criteria/).
- `TR.FinancialScope` accepts an explicit subject/basis: project total, company round target, desired investor contribution or licensing terms. It formats currency, period, scope, estimate date and null distinctly; it never divides a round target into invented checks or derives shares. `TR.FundingRequestCard` shows one raise with multiple invention links rather than repeating the raise per invention. These contracts come from the TemuRiset domain; token/theme changes cannot alter them. — Product-specific inference from the current PRD, with consistent component reuse motivated by [GOV.UK](https://design-system.service.gov.uk/components/).
- `TR.RequirementRow` receives PASS, FAIL, UNKNOWN or NOT_APPLICABLE plus stage, verification mode, reason and next action. `TR.FactSource` distinguishes current/planned/requested from source-reported/provided/reviewed. `TR.DocumentItem` displays file availability/security, extraction status, review status and sharing separately. A safe scan can be available while extraction needs manual input. Prefer concise text plus one meaningful icon over a stack of colored badges. — Product-specific state contract using the documented [component/pattern distinction](https://design-system.service.gov.uk/components/).
- `TR.SaveState` distinguishes changed locally, saving, saved with time, failed and version conflict. It must not claim server saving in a browser-only simulation. `TR.VersionConflict` preserves the user's nonsecret draft and offers comparison/reload or copy/retry. Revision items allow candid “Perlu diskusi” and “Belum dapat dipenuhi” responses without displaying approval. — Proposed recovery semantics; [GOV.UK task-list guidance](https://design-system.service.gov.uk/components/task-list/) supports separating resumable work from summaries and ordered steps.
- `TR.ScheduleSlotList` uses a simple 2–5-slot list, explicit timezone, duration and accepted/proposed distinction. Selection remains draft until explicit acceptance succeeds. `TR.PartnershipConsent` displays one summary version, proposed public-field ceiling, each party's choices, effective intersection and pending confirmation. Narrowing visibility takes effect without pretending it recalls prior downloads. Both components need conflict/pending/expired states instead of a decorative success badge. — Product-specific proposed contracts, subject to the same [in-context usability requirement](https://design-system.service.gov.uk/community/contribution-criteria/).

### Gaps

- These contracts have no implemented component API or observed interaction evidence yet. Names are a proposed stable inventory, not proof that components exist in Claude, React or a shared package.
- The best Indonesian labels for “invention,” “mandate” and financing distinctions still require task-based testing with inventors and investors.

## What workbench, export and consumption evidence makes this a reusable system?

### Takeaway

Require a working component-and-pattern reference, explicit binding/version records and a small consuming sample. A swatch sheet, manifest or matching screenshot alone cannot establish functional reuse or accessibility.

### Cited Findings

- USWDS's maturity model separates principles, guidance and code adoption. It explicitly notes that the presence of a stylesheet or prefixed classes identifies use but does not establish usability or accessibility; implementation must be checked in context. — [USWDS maturity model](https://designsystem.digital.gov/maturity-model/).
- GOV.UK requires context-specific usability and consistency evidence, plus browsers, assistive technologies and devices appropriate to the component, before treating a pattern as ready. — [GOV.UK contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/).

### Inferences

- Require an interactive workbench containing every implemented primitive/domain component in default, focus, selected, disabled-with-reason, loading, validation-error and recoverable-failure states where applicable. Keep independent axes independent: an UNKNOWN requirement can coexist with saved data, a pending counterpart and a failed notification. State demos must be operable, not screenshots labelled as interactive. — Proposed validation consequence of [USWDS in-context checking](https://designsystem.digital.gov/maturity-model/) and [GOV.UK readiness criteria](https://design-system.service.gov.uk/community/contribution-criteria/).
- Include four bounded pattern assemblies: discovery card plus requirement detail; four-step invention editor with project-versus-company financial fields; pitch workspace with revision/document disclosure; and scheduling/relationship confirmation controls. These demonstrate reuse without building the entire application during the system stage. Use the PRD's fictional examples, including one raise linked to two inventions, and natural Indonesian copy. — Proposed evidence-led scope based on [GOV.UK reusable patterns](https://design-system.service.gov.uk/components/).
- Deliver `temuriset-design-system.tokens.json`, a human-readable system guide, a manifest, component inventory/source when available, a runnable workbench, validation evidence and exact consumption instructions. The manifest records DS identity/version/status, token format, supplied artifact/source identifier, component IDs, supported scope and known limitations; credentials never belong there. Source export and editor preview need separate checks because one can work while the other fails. — Proposed portable package, informed by [DTCG exchange format](https://www.designtokens.org/tr/2025.10/format/) and [USWDS implementation assessment](https://designsystem.digital.gov/maturity-model/).
- Start DS version `1.0.0-draft` until checks/review are recorded, independent of PRD, application and composition versions. A consuming sample must use an actual supplied source or artifact, record token/component IDs, and show a controlled shared-token change reaching the relevant previews. If the environment only supports a portable reference, label it as such and document manual mapping. Never claim registered-system inheritance, organization defaults or automatic synchronization without an observed binding. — Proposed proof requirement from [USWDS's adoption-versus-quality distinction](https://designsystem.digital.gov/maturity-model/).
- Version changes should list added/deprecated/changed token and component contracts, compatibility, migration mappings and consumer update instructions. A new brand changes allowed values; a changed interaction contract needs explicit migration. Recheck each supported brand's rendered contrast and component states. Publishing new source does not establish that an existing app consumes it. — Proposed maintenance process informed by [DTCG deprecation semantics](https://www.designtokens.org/tr/2025.10/format/) and [Carbon stable roles](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview).

### Gaps

- No system registration, workbench, binding, exports, theme switching, browser accessibility or participant test was run here. Expected validation results must start NOT RUN, with simulated data provenance tracked separately from PASS/FAIL.
- This research does not establish Claude's account-specific design-system capabilities. The dedicated platform-workflow research must determine supported attachment/import/export paths, and the actual session must still verify availability.
