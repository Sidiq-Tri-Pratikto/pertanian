# Paired backup and restore

Run these commands from a trusted operator host or runner with controlled access to the private backend network. Use Python 3.13 with the API's locked boto3 dependency, GnuPG with integrity-protected symmetric encryption, and PostgreSQL client tools compatible with the source server. Supply credentials through a secret store. The example file lists the inputs without secret values. Never put credentials, the encryption passphrase, or decrypted contents in command arguments, logs or workflow artifacts.

1. Stop and fence every writer to both PostgreSQL and the private S3 bucket, including API, worker, integration jobs, and direct bucket credentials. Preserve the fence until capture completes. Supply an absolute executable as `BACKUP_QUIESCENCE_CHECK`. It must verify the environment-specific fence and return nonzero if it cannot. The tool checks the fence before, between, and after capture and rejects a changed object inventory. The Compose checker in this folder verifies stopped API/worker/migrate containers and requires the operator to confirm the separate S3 write fence. Quiescence requires control of both systems.
2. Use a read-only PostgreSQL backup role, an S3 role limited to listing and reading the source bucket, and a private output directory (mode `0700`) on encrypted local storage. Point `BACKUP_PASSPHRASE_FILE` at a regular private file (mode `0600`) containing a generated high-entropy passphrase. The tool rejects writable-by-others or symlink destinations. Keep passphrases in the secret store independently of archives. Retain old keys while their archives are retained. A lost key means those archives cannot be decrypted.
3. Run `backup.sh` with those inputs. Store its encrypted archive in the dedicated backup repository, with access controls and provider encryption at rest. Record the SHA-256, source identity, UTC snapshot, release, and schema in the separately access-controlled inventory. Copy the expected digest for restore from that trusted inventory. A digest beside the downloaded archive is not a trust anchor.
4. Run `backup.sh --prune` with the same directory to preview expiration. Run `backup.sh --prune --apply` only after independently confirming a successful retained backup and that the retention window has passed. The command only removes regular encrypted archives with the reserved basename pattern from the backup directory. It does not prune S3 or a database. Apply the equivalent lifecycle in the dedicated backup repository.
5. Provision a fresh, private bucket named `temuriset-restore-<id>` and a fresh PostgreSQL database named `temuriset_restore_<id>`, with the same unique ID. Use a target role that owns only that database and an S3 role scoped only to that isolated bucket. Keep the targets offline and dedicated to the drill until verification. Set `TMPDIR` to an operator-only directory on encrypted local storage and run `restore.sh --archive /absolute/path/to/encrypted-archive.tar.gpg --sha256 <trusted-digest>`. The tool verifies the digest, decrypts in a private temporary directory, verifies the archive and all checksums, and requires empty targets before it writes. It verifies the restored Alembic head, object inventory and every object hash before reporting success. A partial restore requires discarding the disposable targets and provisioning a fresh pair. The scripts never cut over traffic.
6. Before any cutover, run application-level checks against the restored pair, including signed-in document access through the gateway with a live grant and refusal without one. Record UTC recovery point, measured restore time, verified data, and observed loss window in the drill record. See [drill.md](drill.md).

PostgreSQL uses its standard TLS settings and the object-store provider controls bucket encryption at rest. Use HTTPS and verified certificates outside a local synthetic drill. Credentials may use PostgreSQL URI authentication, a protected `PGPASSFILE`, or the AWS credential chain as applicable. Do not source any file shipped with an archive.
